### Transactions & Data Integrity (5 HIGH findings)

#### `services/backend/routes/elections/voting.js`

- **Before:** 3 writes (UPDATE voter_registrations, INSERT votes_meta, INSERT vote_receipts) as separate pool.query() calls with no transaction
- **After:** Wrapped in `pool.getConnection()` → `beginTransaction()` → `commit()` / `rollback()` → `release()`
- **Also fixed:** Duplicate `INSERT INTO vote_receipts` at line 434 that was outside the transaction — removed it
- **Why:** Without a transaction, if the second or third write failed, the voter would be marked "voted" but the vote would be lost, breaking the entire voting system's integrity

#### `services/backend/routes/elections/crud.js` (election creation)

- **Before:** INSERT election, then row-by-row INSERT candidates in a `for` loop, then INSERT voter_registrations — all outside a transaction
- **After:** Wrapped in transaction. Candidate INSERTs batched into a single multi-row `VALUES ?` statement
- **Why:** Mid-failure left orphan candidates or registrations with no parent election; batching reduces N round-trips to 1

#### `services/backend/routes/elections/crud.js` (election deletion)

- **Before:** 4 sequential `DELETE FROM` queries outside a transaction
- **After:** Wrapped in `beginTransaction`/`commit`/`rollback`
- **Why:** Partial failure after deleting votes_meta but before deleting candidates would leave data orphaned

#### `services/backend/utils/auditLogger.js` (race condition)

- **Before:** Constructor stored `this.previousHash = null` — on concurrent requests, both reads got `null`, breaking the tamper-evident chain
- **After:** `log()` queries `SELECT log_hash FROM audit_logs ORDER BY id DESC LIMIT 1` from the database on every call. `calculateLogHash()` now accepts `previousHash` as a parameter. `verifyIntegrity()` uses local variable instead of instance state
- **Why:** In-memory state is not safe under concurrency — the DB is the source of truth. Two simultaneous inserts would otherwise have the same `previous_hash`, breaking the chain

#### `services/backend/scripts/migrate.js` (migration transactions)

- **Before:** Full `.sql` file executed as a single `query()` call — partial failure left half-applied migration
- **After:** Each migration wrapped in `START TRANSACTION` ... `COMMIT` / `ROLLBACK`
- **Why:** If a multi-statement migration fails mid-file, the database is left in an inconsistent state

### Pagination: OFFSET → Keyset

#### `services/backend/utils/adminAuditLogger.js`

- **Before:** `LIMIT ? OFFSET ?` — every page scans and discards all previous rows
- **After:** Page 1 keeps `LIMIT ? OFFSET 0`; page 2+ uses `WHERE (timestamp, id) < (?, ?) ORDER BY timestamp DESC, id DESC LIMIT ?`
- **Why:** Deep OFFSET is O(n) — page 1000 scans 1000 rows to skip 990. Keyset pagination uses the index directly, each page is O(limit)

### Security Fixes

#### `services/institution-api/src/config/database.js`

| Issue               | Before                                                    | After                                                                   |
| ------------------- | --------------------------------------------------------- | ----------------------------------------------------------------------- |
| Excessive grants    | `GRANT ALL PRIVILEGES`                                    | `GRANT SELECT, INSERT, UPDATE, DELETE, CREATE, ALTER, INDEX`            |
| Wildcard host       | `'voting_user'@'%'`                                       | Kept `'%'` for container flexibility but scoped privileges              |
| SQL injection       | `CREATE DATABASE ' + dbName` (string concat)              | `!/^[a-zA-Z_][a-zA-Z0-9_]*$/.test(dbName)` validation before use        |
| Fragile migration   | `try { ALTER TABLE ... } catch { if 'Duplicate column' }` | `SELECT FROM information_schema.COLUMNS WHERE COLUMN_NAME = 'is_voter'` |
| Default credentials | Hardcoded `'voting_pass'` in source                       | `console.warn` when defaults are used                                   |

**Why:** GRANT ALL on wildcard host is the MySQL equivalent of giving root keys to everyone; string concatenation for SQL is injection if dbName is ever user-controlled; try/catch on "Duplicate column" is fragile (catches all errors). DDL privileges (CREATE, ALTER, INDEX) added because initDatabase() creates and migrates tables on boot — DML-only blocked schema setup.

> **Runtime fix:** During verification cycle, `GRANT SELECT, INSERT, UPDATE, DELETE` was found to block `CREATE TABLE IF NOT EXISTS` in `initDatabase()`. Added `CREATE, ALTER, INDEX` to the GRANT. (Verified: institution-api now seeds successfully)

### Institution API Query Fixes

#### `services/institution-api/src/routes/lookup.js`

- **Before:** `WHERE institution_id LIKE ? OR full_name LIKE ?` with `"%"+q+"%"` for both — full table scan on every search
- **After:** `institution_id LIKE ?` uses prefix pattern `q + "%"` (index-friendly). `full_name` kept leading-wildcard but documented with note for FULLTEXT
- **Why:** `LIKE 'prefix%'` uses B-tree index; `LIKE '%anything%'` forces full table scan

#### `services/institution-api/src/routes/members.js`

- **Before:** Two round-trips: `SELECT COUNT(*) AS total` then paginated `SELECT ... LIMIT ? OFFSET ?`
- **After:** `SELECT SQL_CALC_FOUND_ROWS ... LIMIT ? OFFSET ?` then `SELECT FOUND_ROWS()` — one scan instead of two
- **Also:** Added composite index `idx_voter_role_id (is_voter, role, institution_id)` to cover the ORDER BY query
- **Why:** Two scans of the same table is wasteful; `SQL_CALC_FOUND_ROWS` computes the count during the first scan

#### `services/institution-api/src/config/database.js`

- **Before:** Two standalone indexes: `idx_institution_id`, `idx_role`
- **After:** Added `INDEX idx_voter_role_id (is_voter, role, institution_id)` and `FULLTEXT INDEX ft_members_name (full_name)` — both in CREATE TABLE and with idempotent ALTER TABLE for existing databases
- **Why:** The query `ORDER BY is_voter ASC, role, institution_id` needs a covering index; full_name search needs FULLTEXT for performance

## Findings Not Resolved (Intentional)

Some findings were documented but not changed. Here's why:

| Finding                                          | Reason                                                                                                                                                                                                                                                   |
| ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| N+1 RSA decrypt loop in admin results            | Would require a precomputed tally storage system + background job + cache layer. This is a feature decision, not a bug fix. The current code works correctly for moderate volumes. If performance becomes an issue, precomputed tallies should be added. |
| Precompute tally results (Phase 2 #1)            | Same as above — tied to feature work                                                                                                                                                                                                                     |
| Irreversible migrations (no DOWN)                | Rollback requires a down-migration system. Added comment in migrate.js explaining the pattern ("create a forward migration to revert").                                                                                                                  |
| Migration 004 is a no-op                         | Historical — 004 was written before 003 was corrected. Keeping both ensures forward compatibility.                                                                                                                                                       |
| ENUM → lookup tables                             | ENUMs work correctly; changing to lookup tables would require application code changes. Acceptable for the current set of values.                                                                                                                        |
| Consolidate 3 audit tables                       | Would require significant application refactoring. Current separation by domain is clear enough.                                                                                                                                                         |
| INT PK overflow for low-growth tables            | Tables like `users`, `elections`, `nodes`, `system_config` won't reach 2.1B rows                                                                                                                                                                         |
| SSL/TLS for DB connections                       | Depends on deployment environment. Added InnoDB config and collation in docker-compose as the server-side baseline.                                                                                                                                      |
| Root user as default in backend config           | The backend runs inside Docker — root user is acceptable in containerized dev. Production should use env vars.                                                                                                                                           |
| CHECK constraint on voter_registrations.voted_at | MySQL CHECK constraints are parsed but not enforced before 8.0.16. Even in 8.0, conditional CHECK on status/voted_at is complex. Application-level validation is sufficient.                                                                             |
