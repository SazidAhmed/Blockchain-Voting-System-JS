## 🔴 Critical Security Issues

| #   | Location                                                     | Issue                                                                              | Why It's a Problem                                                                                                                              | How to Fix                                                                                  |
| --- | ------------------------------------------------------------ | ---------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| 1   | `services/blockchain-node/index.js:100-103`                  | Fake cryptographic key pair — private/public keys are independent random strings   | No mathematical relationship between keys. Block signing/verification trust model is completely broken.                                         | Use `elliptic` library (already imported) to generate proper ECDSA P-256 key pair           |
| 2   | `services/blockchain-node/src/core/block.js:68-81`           | HMAC-SHA256 used for block signing instead of asymmetric ECDSA                     | HMAC is symmetric — any node with the shared key can forge any validator's signature. No non-repudiation.                                       | Use ECDSA P-256 for block signing via `elliptic` library                                    |
| 3   | `services/blockchain-node/src/network/peerManager.js:92-145` | Socket.IO peer connections have no authentication                                  | Any node can connect and emit arbitrary messages (VOTE_BROADCAST, BLOCK_BROADCAST). Attacker can participate in consensus and forge data.       | Add Socket.IO middleware that verifies peer identity via signed challenge or API key        |
| 4   | `services/blockchain-node/src/core/blockchain.js:212-217`    | `verifyVoteSignature` always returns `true` after null check                       | Vote signature verification is completely stubbed out. Anyone can forge a vote.                                                                 | Implement actual ECDSA P-256 signature verification using voter's public key                |
| 5   | `services/backend/routes/elections/voting.js:307-353`        | Legacy vote flow accepts client-provided `privateKey` in request body              | Client sends HMAC private key over wire in plaintext. MITM attacker steals the key.                                                             | Remove legacy flow entirely. Force all votes through client-side signing flow.              |
| 6   | `services/backend/utils/signing.js:8-13`                     | `generateKeypair()` generates random 32-byte hex strings, not actual key pairs     | Function name is misleading — returns two random hex strings with no mathematical relationship. Any caller expecting real keys gets bogus ones. | Rename to `generateSeedMaterial()` or implement actual ECDSA key generation                 |
| 7   | `services/backend/utils/signing.js:25-28`                    | `signData()` uses HMAC-SHA256 (symmetric), not digital signature                   | HMAC is symmetric MAC, not asymmetric signature. Server can forge votes for any user. No non-repudiation.                                       | Remove legacy flow. Use ECDSA signatures from the client-side crypto flow.                  |
| 8   | `services/backend/routes/elections/voting.js:124-128`        | Nullifier derivation falls back to `JWT_SECRET` when `NULLIFIER_SECRET` is not set | If JWT_SECRET is compromised, nullifier generation is also compromised. Attacker can predict nullifiers and double-vote.                        | Require `NULLIFIER_SECRET` in .env, fail startup if missing. Never fall back to JWT_SECRET. |
| 9   | `services/backend/routes/elections/voting.js:239-304`        | Client-provided nullifier has no cryptographic verification                        | Client can submit any 64-char hex string as nullifier. Server only checks uniqueness. Malicious client can reuse leaked nullifiers.             | Derive nullifier server-side from userId+electionId+secret and verify against client value  |
| 10  | `services/backend/utils/signing.js:20-22`                    | `encryptBallot()` is SHA-256 hash, not encryption                                  | SHA-256 is deterministic. Anyone with `electionPublicKey` (returned by API) can brute-force candidate ID guesses.                               | Server should not expose this function. Client encrypts with RSA-OAEP before sending.       |
| 11  | `services/backend/middleware/auditMiddleware.js:20`          | Audit logs spread entire `req.body` including sensitive fields                     | Passwords, private keys logged in plaintext to `admin_audit_logs.changes`. DB readers steal credentials.                                        | Whitelist fields to log. Strip known secret fields.                                         |
| 12  | `services/institution-api/src/routes/members.js:71`          | GET /api/members exposes all member PII without authentication                     | Anyone can enumerate members: full_name, email, role, department. PII leak with no rate limiting.                                               | Add `apiKeyAuth` middleware to the route                                                    |
| 13  | `services/blockchain-node/src/routes/merkle.js`              | All Merkle endpoints have no authentication                                        | Attackers can enumerate nullifiers, run batch verifications, leak vote hashes for all elections.                                                | Apply `apiKeyAuth` middleware and rate limiting to all merkle routes                        |
| 14  | `services/blockchain-node/src/routes/chain.js:7-10`          | Full chain exposed via `/chain` endpoint as mutable reference                      | External code can mutate chain array directly, bypassing all validation. Full encrypted ballot data exposed.                                    | Return deep copy. Apply `apiKeyAuth`. Implement `toJSON()` to strip sensitive fields.       |

2. Remove legacy vote flow that sends privateKey over the wire in backend
3. Add peer authentication to Socket.IO in blockchain-node
4. Fix `verifyVoteSignature` stub that always returns `true`
5. Require `NULLIFIER_SECRET` env var (stop falling back to JWT_SECRET)
